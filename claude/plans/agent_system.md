# VariantGrid as an agent-legible system

Written by Claude Fable 5 (claude-fable-5), 2026-08-31

Issue: https://github.com/SACGF/variantgrid/issues/1816

This is written from the driver's seat: what I, as the agent doing most of the commits on this repo,
would need to understand a situation accurately, act on it with confidence, verify cheaply, and leave the
system better than I found it. It is grounded in what is actually here today (surveyed 2026-08-31 on
`vg-test2`), and it proposes one coherent design rather than a list of nice-to-haves.

---

## 1. What "agent-ergonomic" means, operationally

Every task I do is the same loop:

```
orient  →  decide  →  act  →  verify  →  report / leave behind
```

and every phase has a resource it burns:

| Phase | Cost | What burns it today |
|---|---|---|
| Orient | tokens read, tool calls | greps to find where a concept lives; reading 2,800-line files to find one method; re-deriving runtime facts (which DB, which VEP, what's running) |
| Decide | wrong assumptions | docs that drifted (readmes 2023–24, research Feb 2026) and 87% of modules with no docstring stating their contract |
| Act | round trips | style/lint feedback only when I remember to run it; patterns (DatatableConfig, nodes, ManualOperation) learned by imitation each time |
| Verify | wall-clock, fidelity | 25-min full suite; no way to see a rendered page; no cheap "show me this object's whole graph" |
| Leave behind | accretion | learnings land in CLAUDE.md by hand ("bot training" commits), memory is per-machine, plans are deleted when done, nothing checks docs against code |

The three properties in the brief map to these directly:

- **Intuitive** – the first place I look is the right place; names in docs, code, UI and tests are the same names.
- **Ergonomic** – each question I ask repeatedly is answered by one command with compact output; each feedback loop is one command and is as fast as it can be.
- **Accretive** – what a session learns is captured *where the next session will look*, in a form that is checked against reality so it cannot silently rot.

## 3. The system model — a tower, not a pile

The unifying idea: **every thing in VariantGrid has a Name, a Place, an Inspector and a Doc — and a
check that the four agree.**

- **Name** – one domain vocabulary used identically in models, docs, UI labels and tests.
- **Place** – a predictable location by kind (model / view / task / command / test / template / static).
- **Inspector** – a command that shows the live state of the thing (an object's graph, a page's render,
  a queue's depth, a setting's origin) in compact, structured form.
- **Doc** – the *why* and the invariants, at the altitude where the reader will be standing, linking
  down to symbols and up to the concept.
- **Agreement** – generated where possible, cited where prose, and checked in CI so drift is a failing
  build rather than a wrong PR three months later.

The tower, bottom to top:

```
L5  Harness       .claude/ hooks, allowlist, skills, subagents; memory policy      (how the agent is wired in)
L4  Operations    settings split, secrets, celery queues, manual gates, migrator, CI, this box
L3  Presentation  URL → view → template → JS; grid engines; previews; forms
L2  Processes     VCF import · annotation (VEP/VAV) · liftover · classification import/sync/export · node updates · seqauto
L1  Data model    Django models + migrations; Guardian perms; managers that cache
L0  Domain        Allele/Variant/Locus · Sample/VCF/Cohort · Gene/Transcript(Version) · Annotation(VAV) · Classification/Modification · Analysis/Node
```

Each layer is legible on its own terms:

| Layer | Name | Place | Inspector | Doc |
|---|---|---|---|---|
| L0 Domain | `claude/domain.md` glossary | — | `vg inspect <thing>` | glossary entry → model → module |
| L1 Data | model names = glossary nouns | `<app>/models/` | `vg map models`, Django admin | model docstring; `<app>/CLAUDE.md` |
| L2 Processes | one noun per pipeline, one state enum | `<app>/tasks/`, `<app>/pipelines/` | `vg status`, `vg logs`, `vg inspect` | runbook per pipeline in `claude/runbooks/` |
| L3 Presentation | URL name = view name = template name | `views/`, `templates/<app>/`, `static_files/default_static/js/<app>/` | `vg page`, `vg browse`, `vg map urls` | `uicore/CLAUDE.md` patterns |
| L4 Ops | env name = hostname | `variantgrid/settings/`, `scripts/`, `manual/` | `vg status`, `vg settings`, `manual_outstanding` | `claude/guides/operations.md` |
| L5 Harness | — | `.claude/` | `vg health` | root `CLAUDE.md` |

Linkage is what makes it a tower: every doc links *down* by citing a path or symbol (`snpdb/models/models_variant.py:Variant`), every module docstring names the concept it serves *up* (the glossary term), and `vg docs check` verifies the downward links resolve. Prose that cannot be checked is kept to the "why".

## 4. Design

### 4.1 Knowledge layer — what I read, in the order I read it

**Root `CLAUDE.md` becomes a constitution with a map.** Cap it around 250 lines. It keeps: the rules
(commits, imports, comments, security posture, testing philosophy) and gains a **"Start here" table**
that routes by task:

| If the task is about… | Read | Then use |
|---|---|---|
| a variant / allele / liftover | `snpdb/CLAUDE.md`, `claude/domain.md#variant` | `vg inspect variant <id>` |
| an analysis node | `analysis/CLAUDE.md` | `vg inspect analysis <id>`, `profile_analysis_nodes` |
| a classification | `classification/CLAUDE.md` | `vg inspect classification <id>` |
| a grid / table | `uicore/CLAUDE.md#grids` | `vg page <url> --queries` |
| a management command that must run on deploy | `manual/__manual_readme.md` | `manual_outstanding` |
| performance on real data | `claude/guides/operations.md#scale` | `vg sql --explain` |

plus a **"This box"** section: hostname, what is running, what is shared with human testers, what is
safe without asking (read-only SQL, `vg page` GETs as the `claude_agent` user, `--keepdb` tests) and what
needs a human (service restarts, `migrate`, VAV changes, anything writing to `snpdb_variant` or
`annotation_variantannotation`). Everything else that is currently detail moves down a level.

**Nested `<app>/CLAUDE.md` for the six core apps** (`snpdb`, `genes`, `annotation`, `analysis`,
`classification`, `upload`) plus `uicore` and `library`. Claude Code loads these automatically when I
read a file under that directory, so they are the natural middle rung. 40–80 lines each, rule-shaped:

```
# snpdb — agent notes
Owns: Variant/Allele/Locus, GenomeBuild, VCF/Sample/Cohort, Lab/Org, liftover, custom columns.
Start with: models/models_variant.py (Variant, Allele), models/models_genome.py, liftover.py, grids.py
Patterns here:
- Variant is build-specific; Allele is the build-independent hub. Never compare Variants across builds.
- Reference variants (ref == alt) exist on purpose (Variant.REFERENCE_ALT). Filter them with ...
- Managers on GenomeBuild/Allele/Lab/Organization cache in production (disabled under UNIT_TEST) — see production_query_count()
Gotchas:
- snpdb_variant is 17M rows on vg-test2 and larger in prod: page by pk, fan out celery tasks (claude/guides/operations.md#scale)
Tests: tests/utils/ has the fixture builders; create a Variant with ...
Deep reference: __snpdb_readme.md (narrative), claude/research/snpdb.md (generated reference)
```

The existing `__<app>_readme.md` stays as the human narrative and is linked, not duplicated.

**`claude/domain.md` — the L0 glossary.** ~40 nouns, one paragraph each: definition, the model, the
module, the invariants that are easy to get wrong, and the UI label if it differs. Allele vs Variant vs
Locus; symbolic variants and SVLEN; reference variants; canonical transcripts and TranscriptVersion;
VariantAnnotationVersion vs annotation pipeline vs VEP version; Classification vs
ClassificationModification, published vs draft, share level; discordance buckets; ImportedAlleleInfo;
Analysis / AnalysisNode / NodeVersion / NodeCount; Cohort vs CohortGenotypeCollection; Lab / Organization /
group_name and Guardian groups. This is the vocabulary every other doc and every `vg` output uses.

**Generated maps in `claude/maps/`, committed, checked in CI.** These are the facts prose keeps
restating and getting wrong. `vg map` writes them as Markdown tables (and JSON with `--json`); `vg map
--check` fails when the committed copy is stale, exactly like `makemigrations --check`:

- `models.md` – per app: model, base classes (TimeStampedModel? GuardianPermissionsMixin?
  PreviewModelMixin?), FKs out, notable managers, row count on this box (optional, `--counts`).
- `urls.md` – URL name → view → template(s) → app; flags API endpoints and `PUBLIC_PATHS` exemptions.
- `commands.md` – management command → category → one-line help → which apps' models it touches.
- `tasks.md` – celery task → queue → module → what enqueues it.
- `signals.md` – signal → sender → receivers (module:function).
- `settings.md` – setting → default → which env files override it.

**Research docs become narrative-only and cite checkably.** Each `claude/research/<app>.md` gets a header
`Verified against <sha> on <date>`; the field-by-field model listings that the maps now own are removed;
what remains is flows, why, history, and traps — each paragraph citing the symbol it describes.
`vg docs check` resolves every backticked path / `module:Symbol` citation in `claude/**/*.md`, `*/CLAUDE.md`
and `*/__*_readme.md` and lists the dead ones. A doc with dead citations is a doc I should not trust; now
I can tell.

**Module contracts.** A module docstring is the cheapest, highest-leverage doc there is because it sits
exactly where I am when I need it. Target the ~80 modules with the highest fan-in first (`vg map` can rank
by import count). The contract states: what the module owns, its entry points, the invariants callers
rely on, and what belongs elsewhere. `vg outline <file>` prints classes/functions with line numbers and
first docstring lines, so the 2,800-line files become navigable without splitting them. Track coverage
as a ratchet in `vg health` (13% today).

### 4.2 Introspection layer — `manage.py vg`

One command family, one name to remember, human-readable by default, `--json` for when I want to feed
it onward. Every subcommand exists because it answers a question I ask repeatedly; the list is closed
until a new repeated question appears.

```
vg status [--json]
    env/settings module, git sha+branch+dirty, DB name/size, enabled builds, current VAV per build,
    VEP version, celery services up/down + queue depths, annotation runs in flight, last 10 ERRORs
    from eventlog, disk free on PRIVATE_DATA_ROOT and annotation dirs, manual tasks outstanding.
    The first thing I run in a session; ~7s.

vg inspect <kind> <id-or-key> [--depth N] [--json]
    An object's whole graph, by domain kind not by table:
      variant 123      → locus, allele, sibling variants per build, annotation per VAV, classifications,
                         tags, samples with genotype (capped), clingen allele, liftover status
      allele CA123 / sample 55 / vcf 21 / classification 510 / analysis 46 (node tree with counts,
      last error per node, cache keys) / gene BRCA1 / transcript NM_000059.4 / user dave / lab X
    Built as a registry of inspectors per kind (same shape as create_fake_data's FAKE_DATA registry),
    each returning nested dicts; the Markdown renderer is shared. Read-only transaction.

vg page <url-or-url-name> [--as user] [--text|--html|--links|--forms|--json] [--queries]
    Renders a page through the Django test Client against the live DB (force_login as claude_agent by
    default), returns status, templates used, and the page as an accessible-text outline (headings,
    tables as pipe rows, forms as field lists). --queries reports production_query_count and the top
    repeated normalized SQL (N+1 detection reusing unittest_utils). No browser, ~1s per page after
    startup. This is how I look at a page.

vg browse <url> [--as user] [--screenshot out.png] [--text] [--wait css]
    The same through Playwright's chromium against gunicorn :8000 with a session minted via
    SessionStore, for DataTables / the analysis DAG / anything JS-rendered. Screenshots go to the
    scratchpad and I Read them.

vg tests [--changed [--base REF]] [--list] [--parallel N]
    Maps changed files to test modules through the first-party import graph (AST, no Django boot):
    a test module is selected if it transitively imports a changed module; template/JS/URL changes
    select the app's test_urls; migrations select the app's whole tests/. Prints manage.py test args
    or runs them. Turns "run the 25-minute suite to be safe" into "run the 40 seconds that matter".

vg logs [--since 10m] [--service gunicorn|celery|beat|all] [--level ERROR] [--grep re]
    Merges /var/log/variantgrid/*.log and the eventlog table into one time-ordered stream.

vg sql [--explain [--analyze]] "<python expr returning a QuerySet>"
    Prints the SQL, runs EXPLAIN (ANALYZE only with an explicit statement timeout) in a READ ONLY
    transaction on the real data. Real-scale plans are the thing this box uniquely offers.

vg settings [NAME] [--diff]
    Value, and the file that last set it, walking the split-settings chain (diffsettings tells me the
    value; this tells me where it came from).

vg map [models|urls|commands|tasks|signals|settings|all] [--app X] [--json] [--check]
vg outline <file.py>
vg docs check
vg health
    Ratchets: module docstring coverage, dead citations, one-off command count, lint line count,
    mypy-strict apps, stale maps, test wall time from last CI run.
```

Startup cost: `map`, `outline`, `docs`, `tests --list` need no database and are pure AST. They are also
exposed through `scripts/vg` (a thin dispatcher: static subcommands run in ~0.3s without booting Django,
the rest delegate to `manage.py vg`). `manage.py vg` remains the canonical, discoverable spelling.

### 4.3 Verification layer — the feedback loops, fastest first

```
edit  →  hook: ruff/eslint on the touched file          (< 1s, automatic)
      →  vg tests --changed                              (10s – 2 min)
      →  vg page / vg browse the affected URL            (1 – 5s)
      →  full suite (CI, or locally in --parallel)       (25 min today; target ≤ 10)
      →  vg status / vg logs after deploy                 (runtime truth)
```

Specifics:

- **`--parallel` for the suite.** Django's parallel runner clones the 77 MB test DB per worker; with
  `--keepdb` this is cheap on Postgres. Try `--parallel 4` locally, then in CI. Tests that share files
  under `data/` or talk to redis/rabbit will surface; fix or mark them serial. The single biggest
  wall-clock win available.
- **Query budgets as first-class assertions.** `production_query_count()` exists; wrap it as
  `self.assertProductionQueries(max_n)` on a shared base TestCase, and have `vg page --queries` print
  the same number so I can measure before I write the assertion.
- **Fixture facade.** The builders in `snpdb/tests/utils`, `genes/tests/utils`,
  `classification/tests/utils`, `annotation/tests/test_data_fake_genes.py` are the answer to "how do I
  conjure a Variant / Sample / Classification / Analysis in three lines" — a question I grep for every
  time. Index them in `claude/guides/testing.md` (one line per builder, what it needs, what it returns)
  and reference that index from each app CLAUDE.md.
- **Fake data for pages.** Extend `create_fake_data` with `vcf` (a small VCF with real-looking
  variants and genotypes through the real import path), `classifications`, and `analysis` so any dev
  box — not just this 160 GB one — has pages worth rendering. Each keeps `--delete`.
- **URL smoke on demand.** `vg pages --app analysis` walks that app's named URLs with sample kwargs,
  the way `URLTestCase` already does, and reports status + query count per page. A pre-PR sanity pass
  that costs seconds.
- **Frontend.** `scripts/linting/run_eslint.sh` exists; the hook runs it per file. `vg browse
  --screenshot` is the visual check; keep the mockup convention (`claude/mockups/`) for design-first
  work, and compare the screenshot against the mockup when one exists.
- **Two tiers of browser verification, clearly separated.** `vg page` / `vg browse` are the per-change,
  local, seconds-scale look at one page. `variantgrid_autotests` stays the deployment-scale regression
  net: it needs a running instance, an `.ini` per target and a Selenium driver, so it belongs after a
  deploy to a test instance, not inside the edit loop. Two things make it agent-usable: a line in the
  "This box" section saying how to run it against `vg-test2` (config name, keyword selection with
  `+edit` / `-edit`), and a `claude/maps/autotests.md` listing which scenarios cover which URL names, so
  `vg tests --changed` can also name the autotest keywords a change touches.

### 4.4 Runtime / operations layer — treating this box as the lab it is

- `vg status` and `vg logs` make the running deployment observable in one call each.
- A dedicated `claude_agent` user in the test deployment (member of `all_users`, no lab) for `vg page`
  / `vg browse`, so what I see is what a normal user sees, and my GETs are attributable in `ViewEvent`.
- `claude/guides/operations.md` collects what is currently only in memory or in people's heads: scale
  facts (row counts per deployment; the liftover OOM; page by pk and fan out), which tables are
  partitioned/archived, where secrets and data roots live, what `restart_services.sh` does, how the
  migrator and manual gates run on upgrade, what a deploy looks like end to end. The four current
  memories move here and are deleted from memory.
- Guardrails belong in the harness (4.5), not in prose: state-changing service commands prompt; `vg`
  itself never writes.

### 4.5 Harness layer — `.claude/` in the repo

Committed, so it applies to every session and every teammate's agent:

- **`settings.json`**
  - `PostToolUse` on Edit/Write: `*.py` → `ruff check <file>` (report; `--fix` only for the safe
    import-order/unused-import rules), `*.js` → eslint on that file, `*.scss` → print the
    reminder that the compiled `.css` needs the same hand-applied change.
  - `PreToolUse` on Bash matching `restart_services|systemctl (restart|stop)|manage.py migrate\b|
    manage.py (vep_run|create_new_variant_annotation_version|liftover_alleles)` → emit a one-line
    warning naming who else uses this box; the permission mode decides.
  - `SessionStart`: print `git status --short | head`, branch, hostname, and the newest file under
    `claude/plans/` — orientation for free, no Django boot.
  - Permission allowlist for the read-only set (git read commands, ruff, `manage.py vg *`,
    `manage.py test --keepdb *`, `gh issue view`, `gh pr view`).
- **Skills** (`.claude/skills/`), few and sharp:
  - `vg-plan` – the plan format from CLAUDE.md, the "Written by" header, the issue link, and the habit
    of citing symbols so `vg docs check` covers plans too.
  - `vg-implement` – the implementation-prompt style (positive phrasing, plan is the spec).
  - `vg-research <app>` – regenerate the narrative research doc for one app: run `vg map --app`, diff
    against the current doc, rewrite only what changed, bump `Verified against`.
  - `vg-run` – what the built-in `run` skill looks for first: how to render/inspect a page here
    (`vg page`, `vg browse`) instead of starting a second server.
- **Subagents** (`.claude/agents/`), two:
  - `db-analyst` – read-only; `vg sql --explain`, row counts, index usage on real data; returns a plan
    summary, never a table dump.
  - `page-checker` – given URLs, renders each with `vg page --queries` before and after a change and
    reports diffs in status, headings, and query counts.
- **Memory policy** (one paragraph in CLAUDE.md): memory is for facts about *this machine or this
  user*; a fact about the project goes in the repo (`claude/guides/`, an app CLAUDE.md, a module
  docstring) and the memory is deleted once it lands there.

### 4.6 Accretion protocol — how a session leaves the system better

A short **Definition of done** in CLAUDE.md, applied to every change:

1. Tests that earn their keep are kept (existing rule), and `vg tests --changed` names them.
2. If I created a module, it has a contract docstring. If I learned a gotcha the hard way, it is one
   line in the relevant app CLAUDE.md, not a memory.
3. `vg map --check` and `vg docs check` pass (CI enforces; a small DB-free job that *does* run on
   `claude/**` and `*.md` changes, which the test job rightly ignores).
4. The plan file records its outcome: a `Status:` line (`draft | approved | in progress | landed <sha> |
   superseded by <plan>`), so a landed plan can be deleted with its knowledge already moved into docs.
5. The report-back ends with "what the next agent should know" — one to three lines; if any of them is a
   durable project fact it goes into the repo in the same change.

**Subtractive accretion.** Audit `fix_*` / `one_off_*` commands against `ManualMigrationTask`
completion on the deployments and delete the finished ones, and squash the migration history at the
same time (238 in snpdb alone; `--keepdb` hides the cost locally but CI and fresh checkouts pay it).
Both are scheduled for after the upcoming major deploy, since deployments still on the old release
need the commands and the migration chain intact. Remaining commands declare
`category = "maintenance" | "import" | "one-off" | "dev" | "ops"` on the Command class so `vg map
commands` groups them. Fewer, labelled commands are a better index than a longer one.

**Ratchets, not campaigns.** `vg health` reports the numbers (docstring coverage, dead citations, lint
lines, one-offs, mypy-strict apps, suite wall time). Each is expected to move in one direction; CI can
fail on regressions for the cheap ones (dead citations, stale maps) once they reach zero.

## 5. Code-shape changes that raise legibility (opportunistic, when touching)

- **God files**: outline and docstring first (4.1); split only when already working in one, and split
  the way `snpdb/models/` and `analysis/models/nodes/` already do — a package with one concept per
  module. `classification/models/classification.py` and `annotation/models/models.py` are the two whose
  splits would pay back soonest.
- **Consistent app skeleton**: document the expected layout once in `claude/guides/app_layout.md`
  (`models/`, `views/`, `tasks/`, `management/commands/`, `tests/` with `utils/`, `templates/<app>/`,
  `static_files/default_static/js/<app>/`) and have `vg map apps` list deviations rather than fixing
  them all at once.
- **Names**: where a UI label, a URL name and a model disagree on a noun (the glossary will surface
  these), rename toward the glossary when the surrounding code is next touched.
- **Cross-app wiring**: every `Signal()` gets a docstring stating who sends it and when; receivers are
  registered in `<app>/signals/` (snpdb already does this) so `vg map signals` is complete.

## 6. Phasing

**Phase 0 — one day, all leverage, no risk**
- Restructure root `CLAUDE.md`: constitution + "Start here" map + "This box" + memory policy +
  definition of done. Move detail down.
- `.claude/settings.json` with the hooks and allowlist.
- `claude/domain.md` first cut (the ~25 nouns I already know cause confusion).
- `claude/guides/operations.md` seeded from the four memories; delete the memories.
- `vg status`, `vg outline`, `vg settings` (small, immediately useful).

**Phase 1 — three to four days**
- `vg map` (all six maps) + `--check` in a DB-free CI job.
- `vg page` with `--queries`; the `claude_agent` user.
- `vg tests --changed`; try `--parallel 4` locally, then CI.
- Nested CLAUDE.md for snpdb, genes, annotation, analysis, classification, upload, uicore, library.
- `claude/guides/testing.md` fixture index.

**Phase 2 — about a week**
- `vg inspect` registry for variant / allele / sample / vcf / classification / analysis / gene / user / lab.
- `vg logs`, `vg browse`, `vg sql --explain`.
- `vg docs check`; slim the research docs to narrative with `Verified against` headers.
- Module contract docstrings for the top-80 fan-in modules.
- Skills (`vg-plan`, `vg-implement`, `vg-research`, `vg-run`) and the two subagents.
- `create_fake_data vcf | classifications | analysis`.

**Phase 3 — ongoing ratchets**
- After the major deploy: retire finished one-off commands, squash migrations; categorise the commands
  that remain.
- mypy per-app strictness, starting with snpdb (already the stated plan in `mypy.ini`).
- God-file splits as touched. `vg health` reviewed monthly.

**How we know it worked.** Pick three representative past issues (a node change, a classification
change, a grid change) and measure, before and after: tool calls before the first correct edit, tokens
read, minutes to a verified change, and whether the session left a doc/docstring behind. Plus the
ratchets: dead citations 0, stale maps 0, docstring coverage climbing, suite time falling.

## 7. Anti-goals and risks

- **A fourth doc system that rots.** The antidote is built in: facts are generated (`vg map`), prose
  cites symbols and is checked (`vg docs check`), and CLAUDE.md is capped. If a piece of documentation
  can be neither generated nor checked, it should be short and sit next to the code.
- **`vg` as a kitchen sink.** Every subcommand corresponds to a question in §4.2. New ones need a
  question that has come up at least three times.
- **CLAUDE.md as a dumping ground.** Bot-training lines go to the app CLAUDE.md that owns the topic;
  the root file routes.
- **Humans second.** Every `vg` output is readable by a person by default; JSON is a flag. App
  CLAUDE.md files are terse enough that a new developer benefits from them too.
- **Writing to the lab by accident.** `vg` opens read-only transactions; the harness warns on
  state-changing commands; the "This box" section says who else is using it.
- **Over-splitting.** Big files are a token cost, not a correctness cost; outlines and docstrings buy
  most of the benefit at a fraction of the churn.
