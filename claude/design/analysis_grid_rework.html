Analysis Grid Rework

Bottom-docked variant grid, horizontal node flow, and where the node editor goes — plus sequencing against the jsPlumb and DataTables migrations.

Recommendation. Bottom-docked full-width grid + horizontal node flow is the right move, and the schema is already reserved for it (analysis_horizontal_mode on both UserSettings and Analysis). For the editor, build Swap (tabbed bottom pane) first: it reuses the existing editor+grid container almost untouched, and since saving a node kicks off a 3–10 s re-compute before the grid refreshes anyway, there is no tight editor-beside-grid feedback loop to preserve, and a hidden Grid tab defers the expensive grid query until it's actually wanted. Decision: build Swap and Drawer together — one editor, two homes (bottom tab, or undocked over the canvas), with a live toggle so both get real use before picking a default. Dock is parked. Implementation plan: claude/plans/analysis_layout_rework_plan.md.

Sequencing. jsPlumb upgrade first (like-for-like), layout rework second, jqGrid→DataTables last — each on its own branch. Reasoning at the bottom.

Current layout reference

Vertical node flow on the left; the right panel is split editor-over-grid. The grid inherits whatever width is left over — typically less than half the screen for a table that wants 15+ columns. Drag the splitters below; note the grid scrollbar.

Dock parked

Horizontal node flow across the top, grid docked along the bottom at full width. The editor keeps a docked pane beside the canvas. Both splitters drag — pull the horizontal one up and the grid gets as tall as you like.

For

  • Lowest risk: same three components, same Split.js machinery, rearranged.
  • Editor always visible — no interaction model to learn.
  • Node editors are real forms (tabs, sub-grids); a docked pane gives them honest width.

Against

  • Editor pane taxes canvas width — the axis horizontal flow needs most.
  • Always-visible buys less than it looks: saving triggers a 3–10 s node re-compute before the grid updates, so editor and grid were never a live feedback pair.
  • Wide analyses will still pan; acceptable, canvas already scrolls.

Drawer building — toggles with Swap

Same bottom-docked grid, but the canvas takes the full top row. Selecting a node slides the editor in over the canvas from the right; close it (or press Esc) and the whole width returns to the graph. Click a node below.

For

  • Full canvas width while browsing the graph; editor appears only when needed.
  • Familiar pattern (n8n, Node-RED, Retool all edit nodes in a side panel).
  • Resizable width; can cover complex editors comfortably.

Against

  • Overlays the right of the graph while open — needs a pin/dock toggle for compare-while-editing workflows.
  • Slightly more state to persist (open/pinned/width) per analysis.

Swap building — toggles with Drawer

Canvas gets the whole top, and the bottom pane is shared: it tabs between editor and grid, each at full width and full pane height. Selecting a node flips to the editor; Save flips back to the grid so you see the result. Click a node, then click Save.

For

  • Cheapest to build: the existing editor+grid container and its paired-loading logic move wholesale; the only new UI is the tab strip.
  • Lazy by construction: a hidden Grid tab defers the expensive grid query (via the existing grid_auto_load/deferred machinery) — editing a chain of nodes issues no grid fetches until you flip to Grid.
  • Editor, grid and canvas each get full width — nothing shares an axis with anything.
  • Matches real usage: analysts mostly browse node results (grid tab stays put as you click around the graph); editing is the occasional detour.

Against

  • Editor and grid are never visible together — but saving already triggers a 3–10 s node re-compute before the grid refreshes, so there was never a live pair to lose. The residual cost is a tab flip when comparing settings against results.
  • Full width is wasted on most editors (they're narrow forms), which is the axis the grid actually needed.
  • Hidden-tab grids need care: a jqGrid sized while hidden gets zero width (DataTables has the same quirk) — resize on tab-show.

Float not as the only mode

The editor as a floating panel that pops up beside the selected node (draggable by its title bar). Click a node below, then drag the panel around.

A fourth idea — the editor sliding out from behind the node card itself parked — looks delightful but doesn't survive contact with the content: cards are 64px wide and editors need ten times that, so the "slide out" immediately becomes a detached panel anyway (i.e. Float), while adding z-order and repaint fights with jsPlumb during drag.

Settings & behaviour notes

  • Already reserved: UserSettings.analysis_horizontal_mode (default for new analyses) and Analysis.analysis_horizontal_mode (what the page actually renders). Per-analysis is right for a deeper reason than taste: saved node positions are authored for an orientation. A vertical DAG is tall and narrow; flipping it to horizontal without touching positions gives a mess.
  • Mode switch on an existing analysis: transpose node positions (swap x/y) as the first pass — a topologically-sorted DAG transposes surprisingly well. Offer "auto-arrange" as the escape hatch.
  • Anchors: vertical mode wires BottomCenter → TopCenter; horizontal becomes RightMiddle → LeftMiddle (and the dual-parent Top Left/Right endpoints for Trio-style nodes become upper/lower on the left edge).
  • Splitter persistence: analysis_panel_fraction can keep meaning "fraction of the primary split" in both modes (canvas/editor today, canvas-row/grid in horizontal mode); the Dock's editor width is one more float.
  • Dual-screen mode composes fine: it already ships editor+grid to a second window, which is the ultimate "grid gets the full width" — horizontal mode just makes single-screen life better.

Sequencing the three jobs

The rule that decides the order: never bundle a library migration with a UX change. A migration is verifiable exactly because current behaviour is the baseline; redesign at the same time and every bug becomes unattributable.

  1. jsPlumb 1.4.1 → Community Edition 5/6 (@jsplumb/browser-ui) — like-for-like

    1.4.1 is from 2013 and the API it exposes no longer exists: the new library is instance-based (newInstance({container})), jQuery-free, and does its own dragging — which absorbs the jquery-ui draggable + multidraggable.js stack (5+ has native drag-selection for multi-node drag). Do this before the layout work so the horizontal anchor/orientation code is written once, against an API that's alive, instead of written for 1.4.1 and immediately ported.

  2. Layout rework — Swap, with Dock/Drawer as optional evolutions

    Mostly templates, CSS and Split.js reconfiguration plus wiring the reserved settings; the existing editor+grid container moves to the bottom pane and gains tabs. jqGrid survives the move: the existing resize plumbing (setGridWidth on splitter drag) keeps working, so the layout doesn't wait on the grid migration. This is the step users actually see — land it second.

  3. jqGrid → DataTables — the big one, in its final home

    The analysis grid is the deepest jqGrid usage in the codebase: custom column collections, server-side sort persistence, exports, tag rendering, variant links. Doing it after the layout means the DataTable is designed once for where it will live — full-width, arbitrary height, Scroller/fixed-header — rather than tuned for the narrow right panel and re-tuned after. The DatatableConfig/RichColumn infrastructure is already the house pattern.

    Swap 2 & 3 only if jqGrid's resize behaviour proves too janky in a freely-draggable pane — that's the one scenario where the grid migration blocks the layout instead of following it.
